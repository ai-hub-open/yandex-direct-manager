## 0. Источник истины (проверено живьём 26.08.2026)

### 0.1. Сервер Wordstat — три инструмента, никакого `topRequests`

Реальный инвентарь сервера `yandex-wordstat` (`wordstat-mcp.aihub.click.ru`):

| Инструмент | Что делает | Параметры |
|---|---|---|
| `wordstat_shows_batch` | Частотность пачкой, **синхронно**. Возвращает `{ result: [{keyword, error, stat, cache_date}], total, pending }` | `keywords` (до **1000** за вызов), `region_id` (int, дефолт 213), `strict` (bool — оператор `!` на каждое слово) |
| `wordstat_shows_batch_submit` | То же асинхронно: возвращает `{id, status:"pending"}` | те же |
| `wordstat_shows_batch_status` | Забрать результат по `id`; `status`: `pending` / `done` / `failed` | `id` |

**Чего на сервере нет:** `top_requests`, `regions`, `dynamics`, `list_regions`.
**Нет полей** `results[]`, `associations[]`, `totalCount`. Есть только `stat` — показов/мес.
Под капотом **не** Yandex Cloud Search API, а шлюз click.ru → `seoapi.seopult.ru`.

Проверка: `wordstat_shows_batch(["картины на холст"], region_id: 225)` →
`{"result":[{"keyword":"картины на холст","error":0,"stat":67401,"cache_date":"2026-08-26"}],"total":1,"pending":0}`.

**Устойчивость:** первый вызов упал с `gateway 502: polling exhausted: upstream ... EOF`,
повтор тем же телом прошёл. Шлюз флапает — нужен ретрай.

### 0.2. Сервер Директа — режимы и подтверждённое поведение

В одной сессии может быть **несколько** серверов Директа в разных режимах:

| Режим | `accounts_get.source` | `forecast_bids` | Чтение отчёта без фильтра |
|---|---|---|---|
| Прямой OAuth Яндекса (`/y/<токен>`) | `yandex-direct` | **работает** | работает |
| Прокси click.ru (`/c/<логин>/<токен>/<id>`) | `click.ru` | ошибка «живёт в Live API v4» | **код 8000** |

Подтверждено:

- `accounts_get` отдаёт список кабинетов с `client_login`; на прокси-подключениях их было 3 и 8.
- `campaigns_get` **без** фильтров работает (внутренняя защита подставляет все `States`).
- `keywords_get` без фильтра → `8000 SelectionCriteria cannot contain an array`.
- `report_campaign` **без** `campaign_ids` → тот же `8000` на обоих прокси-подключениях;
  с `campaign_ids` — ок. На прямом OAuth проходит и без ids. **Это новое: в текущей
  документации отчёты в правило фильтра не входят.**
- `adextensions_get` без фильтров работает штатно (исключение, как и `campaigns_get`).
- `dictionaries_regions` отдаёт **2,87 МБ / 104 072 строки** — клиент обрезает ответ.
- `adimages_add`: схема параметров — `file_path`, `name`, `crop`, `crop_offset`, `dry_run`.
  **URL-параметра нет.**
- `dry_run` присутствует у всех мутирующих инструментов — как и описано.
- Поведение «читающий инструмент без фильтра чинится сам» (обещание MCP 0.5.1)
  на хостовых инстансах **ещё не наступило** — ведут себя как 0.5.0.

### 2.2. Новая методика Шага 3 (главное содержательное изменение)

**Принцип, который нужно провести по всем файлам:** MCP Wordstat — это **верификатор
частотностей, а не источник расширения семантики**. Расширение приходит откуда-то ещё.

Новая цепочка приоритетов Шага 3:

| # | Путь расширения | Условие | Частотности |
|---|---|---|---|
| 1 | `scripts/wordstat_api.py --mode semantics` (Cloud Search API, `topRequests` → `results` + `associations`, рекурсия волнами) | есть `WORDSTAT_API_KEY` + `WORDSTAT_FOLDER_ID` и запуск кода | из того же ответа |
| 2 | **Комбинаторная генерация кандидатов** из `01_masks.json` + пакетный пробив через MCP | есть только MCP | `wordstat_shows_batch` |
| 3 | Выгрузка из стороннего сервиса / список от маркетолога | нет ни того, ни другого | `wordstat_shows_batch`, если MCP есть |
| 4 | Браузерный пробив (`wordstat-browser.md`) | нет MCP и нет ключа | вручную |
