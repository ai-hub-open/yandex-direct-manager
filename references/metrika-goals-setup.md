# Metrika Goals Setup — настройка Метрики и целей под кампанию

Используется на Шаге 7 пайплайна (между минусами и объявлениями). Без этого этапа кампания не сможет работать на конверсии.

Метрика — **глаза** Директа: она видит, что пользователь сделал после клика. Цели — **что мы считаем конверсией**. Без правильных целей:
- Автостратегии Директа не учатся (`bidding-strategy` Шаг 9, Фаза 3 застрянет навсегда)
- Расчёт CPL/CAC невозможен
- Стратегия «Оплата за конверсии» не запустится (а для сетевой части ЕПК она основная)
- Ретаргетинг по сегментам сайта не работает
- В отчётах Директа нет числа конверсий — оптимизировать нечего

## Главный принцип

Цели — это **не «всё, что можно отследить»**, а **специально подобранный набор под конкретную кампанию**:

| Тип цели | Что считается | Зачем |
|----------|---------------|-------|
| **Макро-конверсия** | Главное действие, на которое оптимизируем (отправка формы, заказ, оплата) | Базовая цель оптимизации. По ней Фаза 3 `bidding-strategy`. |
| **Микро-конверсия** | Промежуточные действия (клик WhatsApp, скролл 75%, добавление в избранное, открытие формы) | Для накопления данных алгоритмом на старте + отладки воронки. |
| **Составная цель** | Связка «А + Б» (например, демо-заявка + start_trial) | Для длинных циклов (B2B SaaS). Защищает от холодных лидов. |
| **Offline-конверсия** | Импортируется из CRM/коллтрекинга (звонок, оплата на счёт) | Для услуг со звонками. Через коллтрекинг отдельно. |

**Главная ошибка** — поставить макро-целью что-то, что массово срабатывает («вход на сайт», «клик по любой кнопке»). Алгоритм оптимизируется в пустоту, считает ботов «конверсиями», бюджет сольётся.

## Что НЕ делаем

- **Коллтрекинг** — отдельная задача (Calltouch/Callibri/Roistat + интеграция с Метрикой как «офлайн-конверсии»). Скилл отмечает «коллтрекинг нужен» в артефакте.
- **JS-код для целей** — все цели через API Метрики или визуальный конструктор. JS-цели (`ym('reachGoal')`) требуют изменения кода сайта — работа разработчика.
- **Электронная коммерция** — Ecommerce-цели требуют `dataLayer` на сайте, отдельная техническая задача.
- **Создание счётчика с нуля** — если Метрики нет совсем, говорим маркетологу «установи через https://metrika.yandex.ru/list/ и подключи аккаунт с Метрикой в интеграциях click.ru — инструкция: https://help.click.ru/97#connect-yandex-metrica» и ждём.

## Чем работаем: MCP Метрики → API → UI

Основной путь — **MCP Метрики** (хостовый сервер aihub.click.ru, в сессии может называться `metrikaCM`, `yandex-metrika` или иначе). Ищи его **по инструменту** `*yandex_metrika_counters_get` / `*yandex_metrika_goals_add`, а не по имени; в средах с отложенной загрузкой — сначала поиск инструмента механизмом среды. Отдельный OAuth-токен Метрики при MCP **не нужен**: доступ идёт через интеграцию Метрики в click.ru.

| Задача | Инструмент MCP |
|---|---|
| Найти счётчик сайта | `yandex_metrika_counters_get({ search: "<домен>", with_goals: true })` |
| Детали счётчика: статус, зеркала, доступ | `yandex_metrika_counter_get({ counter_id, fields: ["goals", "mirrors"] })` |
| Цели + живость за N дней | `yandex_metrika_goals_get({ counter_id, stats_days: 30 })` → `reaches`, `conversion_rate` |
| Видит ли счётчик кабинет Директа | `yandex_metrika_direct_clients_get({ counter_id })` → `chief_login` |
| Создать / изменить цель | `yandex_metrika_goals_add` / `yandex_metrika_goals_update` — **сначала `dry_run: true`** |
| Сегменты под ретаргетинг | `yandex_metrika_segments_get` / `yandex_metrika_segments_add` (`dry_run: true` на гейте) |
| Отчёты (история трафика, фразы, расходы Директа) | `yandex_metrika_report` / `yandex_metrika_report_bytime` |
| Удалить цель / сегмент | `*_delete` — **скилл не удаляет**: мусорные цели только не используем (удаление ломает чужие кампании, которые на них оптимизируются) |

**Серверов Метрики в сессии может быть несколько** (`metrikaCM`, `MetrikaDevadent` — разные пользователи click.ru). Сервер выбирается на Шаге 0.5Б и лежит в `_state.json` → `metrika_server`; на Шаге 7 зови инструменты **только этого сервера**. Не нашёл счётчик на нём — не переключайся молча на другой: скажи маркетологу и спроси.

`account` в вызовах обычно не нужен — сервер сам находит аккаунт, которому доступен счётчик. Если у маркетолога несколько интеграций Метрики — `yandex_metrika_accounts_get` покажет список.

**Цепочка фолбеков:**
1. **MCP Метрики есть и отвечает** — весь шаг через него.
2. **MCP отвечает «У пользователя click.ru не подключена Яндекс Метрика»** (`accounts_get` вернул пустой `accounts`) — это не «MCP нет», а не подключена интеграция. Скажи маркетологу **дословно со ссылкой**: «Подключи аккаунт Яндекса с Метрикой в интеграциях click.ru по инструкции https://help.click.ru/97#connect-yandex-metrica — и продолжим». Без ссылки не отправляй: где подключается интеграция, без инструкции не найти. Ждать некогда → переходи к п. 3/4 с пометкой о пропуске.
3. **MCP нет, есть OAuth-токен Метрики** (scope `metrika-manage`, write) — те же действия через Management API (`GET /management/v1/counters`, `GET|POST /management/v1/counter/{id}/goals`), если среда умеет сетевые вызовы.
4. **Ничего нет** — режим «инструкции для UI»: аудит по словам маркетолога, план целей, маркетолог заводит цели руками и присылает `goal_id`.

## Вход

1. **URL сайта** — из `00_brief.md` (поле 1).
2. **`counter_id`** — если найден на Шаге 0.5 (`_state.json` → `metrika_counter_id`), берём оттуда и не ищем заново.
3. **Список кампаний** — из `05_campaign_structure.json` (Шаг 5).
4. **Тип ниши** — определит шаблон целей.
5. **Тип конверсии из брифа** (поле 8 в `00_brief.md`) — форма / звонок / онлайн-оплата / триал / другое.
6. **`direct_client_login`** из `_state.json` — для проверки, что счётчик видит кабинет.

Если входа не хватает:
```
Чтобы настроить Метрику и цели:
1. URL сайта (из брифа, подтверди если изменился): ?
2. Главная конверсия — что считаем заявкой? Форма / звонок / online-оплата / триал?
3. Если со звонками — подключён коллтрекинг (Calltouch/Callibri/Roistat)?
(Только если MCP Метрики нет: OAuth-токен Метрики с правом write, scope metrika-manage — без него цели заводишь руками по моей инструкции.)
```

## Фаза 1. Аудит счётчика

1. **Найти счётчик.** `counters_get({ search: "<домен без www>", with_goals: true })`. Ищем по домену **и** по зеркалам: в ответе у каждого счётчика сайт и зеркала, уровень доступа (`own` / `edit` / `view`) и аккаунт.
   - Найден один — берём. Несколько — см. «Несколько счётчиков на одном сайте».
   - Не найден в доступных — это ещё **не** «Метрики нет»: счётчик может стоять на сайте, но жить в чужом аккаунте. Проверь сайт инструментом чтения страниц (тег `mc.yandex.ru/metrika/tag.js`, `ym(<id>, "init"`). Тег есть, а в MCP счётчика нет → «Счётчик принадлежит другому аккаунту». Тега нет → алярма «Метрики нет».
   - Нет ни MCP, ни чтения страниц — спроси `counter_id` у маркетолога, пометь пропуск, **алярму не снимай**.
2. **Проверить, что счётчик живой.** `counter_get({ counter_id, fields: ["mirrors"] })` → статус (`Active`), код установлен; плюс `report_bytime({ counter_id, metrics: ["ym:s:visits"], date1: "7daysAgo", group: "day" })` — визиты есть каждый день. Нули по визитам при живом сайте = код сломан или снят, это алярма того же уровня, что «Метрики нет».
3. **Права.** `permission: view` — создавать цели нельзя → режим рекомендаций (см. «Особые случаи»). `own` / `edit` — работаем.
4. **Цели с живостью.** `goals_get({ counter_id, stats_days: 30 })` — у каждой цели `reaches` и `conversion_rate` за 30 дней. Это главное, что даёт MCP: классифицируем не по названию, а по факту:
   - **мёртвая** — `reaches = 0` за 30 дней при живом трафике: условие не срабатывает (сменился URL «спасибо», удалили JS-событие). Не используем, в аудите — «проверить условие».
   - **мусорная** — `conversion_rate` > 30–40 % (срабатывает почти у всех: «вход на сайт», «любой клик», «2 страницы») → `not_usable_for_optimization`.
   - **пригодная** — осмысленное условие и правдоподобная конверсия (обычно 0,5–10 %).
   - **Объём** (`reaches` / 4,3 = конверсий в неделю) запиши для каждой пригодной цели — он нужен Шагу 9 (порог ≥10 конв/нед для оплаты за конверсии).
5. **Связь с Директом.** `direct_clients_get({ counter_id })` — есть ли среди клиентов наш `direct_client_login` (`chief_login`). Нет — значит, по этому кабинету Директа счётчик ещё не видел ни одной кампании; это нормально для нового кабинета, привязка появится на Шаге 10 через `counter_ids`. Плюс `campaigns_get({ include_strategy: true })` на сервере Директа — `CounterIds` / `PriorityGoals` действующих кампаний: кто уже оптимизируется на какие цели.

Артефакт: `07_metrika_audit.md` — счётчик (id, домен, зеркала, доступ, визиты/день), таблица целей: `goal_id | название | тип | условие | reaches 30д | конв. % | конв/нед | вердикт` + связь с Директом.

## Фаза 2. Проектирование целей под кампанию

Для каждой выбранной кампании определяем нужный набор по шаблону ниши.

**Стандартный набор:**
- 1 макро-конверсия (то, по чему меряем эффективность)
- 2-3 микро-конверсии (для прогрева алгоритма на старте)

См. «Шаблоны целей по нишам» ниже.

**Для каждой цели в плане:**
```
- Название: <ясное, например «Заявка на демо CRM-Flow»>
- Тип в Метрике: url / phone / messenger / file / number / visit_duration / step / action (см. таблицу «Типы целей»)
- Условие срабатывания: <конкретное>
- Категория: макро / микро / составная
- Привязка к кампаниям: <campaign_key из 05_campaign_structure.json — или ВСЕ>
- Ценность конверсии, ₽: <из брифа, поле «ценность целевого действия»; нет данных — null>
- Статус: existing / need_to_create / need_js_dev
```

**Про ценность конверсии.** Она нужна на Шаге 10: приоритетные цели кампании (`priority_goals`) передаются в Директ парой «цель + её ценность», и без ценности параметр не принимается. Берём её из брифа (средний чек или ценность целевого действия), **не выдумываем**. Если маркетолог ценность не назвал — ставим `null`, и на Шаге 10 приоритетные цели просто не передаются: счётчик к кампании привяжется всё равно, а автостратегия будет учиться на конверсиях без весов. Это честнее, чем подставить выдуманное число, по которому алгоритм начнёт оптимизировать не туда.

**Объём решает, что будет макро.** Из аудита у каждой пригодной цели есть конверсий/нед. Если у главной цели меньше ~10 конв/нед на весь сайт — на старте кампания на неё не обучится: в плане помечаем её макро для отчётов, а для оптимизации на Шаге 9 предлагаем более частую цель воронки (или пакетную стратегию). Новые цели объёма не имеют — пиши `volume: unknown`, не выдумывай.

**Сегменты под ретаргетинг (если в структуре Шага 5 есть ретаргет-кампания).** Сначала `segments_get` — часто нужный сегмент уже есть. Нет — проектируем 1–3 сегмента в синтаксисе `filters`, например:
- «Пришли с рекламы, смотрели цены»: `ym:s:lastsignTrafficSource=='ad' AND ym:s:startURL=@'/ceny'`;
- «Были на сайте, не дошли до макро-цели» — выражение по цели собери под конкретный `goal_id`.

**Проверяй выражение отчётом, а не только `dry_run`:** `dry_run` показывает тело запроса, но не валидирует условие. `report({ counter_id, filters: "<выражение>", metrics: ["ym:s:users"], date1: "30daysAgo" })` — ошибка синтаксиса всплывёт сразу, а `users` покажет размер аудитории (меньше ~100 человек за 30 дней — ретаргет в РСЯ толком не откроется, скажи об этом).
Сегменты создаются на том же гейте, что и цели. ⚠️ Условие ретаргетинга в Директе из сегмента MCP Директа не создаёт — в `10_launch_log.md` уходит ручным пунктом с `segment_id`.

Артефакт: `07_metrika_goals_plan.md`.

## Фаза 3. Гейт маркетолога перед созданием

⚠️ Цель начинает считать конверсии сразу после создания и остаётся в счётчике — «лишнего» не создаём.

Перед гейтом прогони **каждую** новую цель и сегмент через `goals_add` / `segments_add` с `dry_run: true`: сервер вернёт тело запроса, ничего не создавая, — маркетолог видит ровно то, что уйдёт в Метрику. Выражения сегментов дополнительно проверь отчётом (см. Фазу 2).

```
Метрика: ✅ счётчик 87654321 (site.ru + 2 зеркала), доступ: edit, ~420 визитов/день
Директ: кабинет porg-xxxx среди клиентов счётчика ✅ / ещё нет (появится после заливки)
Существующие цели: 12
  пригодные — 3: «Заявка» (38 конв/30д ≈ 9/нед), «Оплата» (11/30д), «Клик WhatsApp» (64/30д)
  мёртвые — 2: «Спасибо за заказ» (0 за 30 дней — проверь URL страницы успеха)
  мусорные — 7: «Вход на сайт» (100 %), «Любой клик» (71 %), …
Создать (dry-run прошёл):
  - «Клик по телефону» — phone
  - «Время на сайте > 1 мин» — visit_duration 60
  - «Скачал прайс» — file
  - составная «Заявка → Оплата» — step
  - сегмент «Был на сайте, без заявки» — для ретаргета РСЯ
Разработчику (action, JS): click-demo-button — сниппет в 07_metrika_audit.md
Звонки как макро — только через коллтрекинг (не подключён?)
```

Прямой вопрос: «Создаём 4 цели и 1 сегмент?» Не двигайся к Фазе 4 без явного «создавай».

## Фаза 4. Создание целей

После «ОК», для каждой `need_to_create` — тот же вызов без `dry_run`:

```
yandex_metrika_goals_add({ counter_id, goal: {...} })
```

**Тела целей** (поле `goal`, одинаково для MCP и Management API `POST /management/v1/counter/{id}/goals`):

```json
// url — посещение страницы
{"name": "Заявка отправлена", "type": "url",
 "conditions": [{"type": "contain", "url": "/thanks"}], "default_price": 3000}

// phone — клик по телефону (условия не нужны: все номера на сайте)
{"name": "Клик по телефону", "type": "phone"}

// messenger — переход в мессенджер
{"name": "Переход в WhatsApp/Telegram", "type": "messenger"}

// visit_duration — время на сайте
{"name": "Время на сайте > 1 мин", "type": "visit_duration", "duration": 60}

// number — глубина просмотра
{"name": "Просмотр 5+ страниц", "type": "number", "depth": 5}

// action — JS-событие ym(<счётчик>, 'reachGoal', 'click-demo')
{"name": "Клик «Заказать демо»", "type": "action",
 "conditions": [{"type": "exact", "url": "click-demo"}]}

// step — составная, 2–5 шагов по порядку воронки
{"name": "Демо → Триал → Активен 7 дней", "type": "step", "steps": [
  {"name": "Заявка на демо", "type": "action", "conditions": [{"type": "exact", "url": "click-demo"}]},
  {"name": "Начал триал", "type": "url", "conditions": [{"type": "contain", "url": "/trial/started"}]},
  {"name": "Активен на 7-й день", "type": "action", "conditions": [{"type": "exact", "url": "day7-active"}]}
]}
```

Условия `phone` / `messenger` / `file` / `social` можно сузить (конкретный номер, конкретный мессенджер) — точный формат сверяй на `dry_run`.

`default_price` — ценность цели в Метрике; ставь ту же, что идёт в `priority_goals` на Шаге 10 (из брифа). Нет ценности — не передавай.

После каждого вызова:
- Запоминаем `goal_id` из ответа
- Логируем «ок» или ошибку в `07_metrika_setup_log.md`
- Ошибка прав (`view`, чужой счётчик) → сразу останавливаемся, говорим маркетологу
- **Финальная сверка:** `goals_get({ counter_id })` — все созданные цели на месте, условия совпадают с планом

Изменить существующую цель (например, мёртвую с устаревшим URL) — `goals_update`, и **только целиком**: поля, которых нет в запросе, Метрика может сбросить. Тоже через `dry_run` и гейт. Удалять цели скилл не удаляет.

Если `need_js_dev` — цель типа `action` **можно** создать сразу (она начнёт считать, как только разработчик поставит событие), но в `07_metrika_audit.md` обязательно: «JS-событие `click-demo-button` нужно поставить разработчику: `ym(<counter_id>, 'reachGoal', 'click-demo-button')`». Пока события нет — такую цель **не** ставим целью оптимизации на Шаге 9.

## Фаза 5. Привязка counter_id и goal_ids к Direct-кампаниям

Делается на Шаге 10, при заливке: параметры `counter_ids` и `priority_goals` передаются прямо в `campaigns_add`. Для уже созданной кампании — тем же набором параметров в `campaigns_update`:

```
campaigns_update({
  id: <ID кампании>,
  campaign_type: "UNIFIED",
  counter_ids: [87654321],
  priority_goals: [{ goal_id: 100001, value: 3000 }]
})
```

1. `counter_ids` — счётчик привязан, Директ видит статистику. **Передаётся всегда.**
2. `priority_goals` — макро-цель с ценностью конверсии: по ней учится автостратегия.
3. Микро-цели идут туда же отдельными элементами, с их собственной ценностью.
4. Для составной цели передаётся её `goal_id` — шаги внутри учитываются автоматически.

## Шаблоны целей по нишам

### Срочный спрос (эвакуатор, такси, аварийный сантехник)

**Главная конверсия:** звонок (90%+), НЕ форма.

**Макро:**
- Клик по телефону — тип `phone` (без разработчика: Метрика сама ловит клики по `tel:`); переход в WhatsApp/Telegram — тип `messenger`
- Offline-конверсия из коллтрекинга (если подключён) — импорт через Calltouch/Callibri/Roistat

**Микро:**
- Открыл «Цены» — `url`, `contain "/ceny" or "/tarify"`
- Открыл калькулятор стоимости — `action`, событие `open_calculator` (JS, разработчик) или `url`, если у калькулятора своя страница
- Время на сайте > 30 секунд — `visit_duration`, `duration: 30`
- Скролл 50% — `action`, событие `scroll_50` (JS, разработчик)

**НЕ использовать:**
- ❌ «Отправка формы» как макро (редко заполняют в срочке)
- ❌ «Добавление в избранное» (нет понятия в нише)
- ❌ Длинные составные (паника + многошаговая воронка несовместимы)

### B2B SaaS (CRM, ERP, бухучёт)

**Главная конверсия:** демо-заявка → активация триала. Цикл длинный → **обязательна составная цель**.

**Макро:**
- Составная «Демо → Триал → Не отменён за 7 дней» — `step`
- Простая «Заявка на демо» — резервная (холодный клик)
- Регистрация (создал аккаунт) — `url`, `contain "/register/success"`

**Микро:**
- Открыл тарифы — `url`, `contain "/tarify"`
- Время > 3 минут — `visit_duration`, `duration: 180`
- Открыл кейсы / «О продукте» — `url`
- Скачал PDF / White Paper — `file` (без разработчика)
- Открыл сравнительную таблицу с конкурентами — `url`

**НЕ использовать:**
- ❌ «Любой клик» (боты)
- ❌ Простая «Заявка на форму» **как единственная макро** (холодный лид в B2B SaaS почти никогда не доходит до оплаты)
- ❌ Цели по времени без скролла (на B2B-сайтах часто открывают и оставляют вкладку)

**Специфика B2B SaaS:** подключить **импорт офлайн-конверсий из CRM** через Метрика → Управление → Загрузка офлайн-конверсий. Позволит видеть в Директе реальные продажи. Без этого CAC посчитать невозможно.

### Премиум-сегмент

**Главная конверсия:** долгий цикл, личное касание (звонок, WhatsApp, личный визит).

**Макро:**
- Клик WhatsApp / Telegram — `messenger`
- Заявка на консультацию (форма) — `url`, страница успеха
- Клик «Записаться на просмотр» — `action`, событие `book_viewing` (JS, разработчик)

**Микро:**
- Добавление в избранное — `action`, событие `add_to_favorites` (JS, разработчик)
- Глубокий просмотр — `number`, `depth: 5`
- Открыл «История бренда / автора» — `url`
- Скролл 75% — `action`, событие `scroll_75` (JS, разработчик)
- Скачал каталог / PDF / прайс — `file`

**НЕ использовать:**
- ❌ «Добавление в корзину» (премиум-продукты редко через корзину)
- ❌ Триггеры «купи сейчас» / «оплати» как макро
- ❌ Микро с быстрыми триггерами (клик <10 сек — премиум-клиент читает дольше)

### Ручная работа / на заказ

**Главная конверсия:** заявка с консультацией мастера.

**Макро:**
- Отправил «Обсудить с художником» — `url`, страница успеха
- Клик WhatsApp / Telegram — `messenger`
- Запросил эскизы по фото — `action`, событие `request_sketches` (JS, разработчик)

**Микро:**
- Открыл портфолио — `url`, `contain "/portfolio"`
- Время на сайте > 1 мин — `visit_duration`, `duration: 60`
- Открыл «Как мы работаем» / «Сроки» — `url`
- Скролл 75% — `action`, событие `scroll_75` (JS, разработчик)
- Просмотр 5+ страниц — `number`, `depth: 5`

### Массовые услуги (доставка, ремонт, клининг)

**Главная конверсия:** заказ или звонок.

**Макро:**
- Оформление заказа (для интернет-магазинов) — `url`, `/order/success`
- Форма «Перезвоните» — `url` страницы успеха или `action`, событие `callback_sent` (JS, разработчик)
- Клик по телефону — `phone`; WhatsApp — `messenger`

**Микро:**
- Добавление в корзину — `action`, событие `add_to_cart` (JS, разработчик; при Ecommerce — уже есть)
- Открыл контакты / адреса — `url`
- Скролл 50% — `action`, событие `scroll_50` (JS, разработчик)
- Открыл калькулятор стоимости — `action` или `url`

### Если ниша не подходит

**Дефолтный набор:**
- 1 макро (главная конверсия из брифа)
- 2-3 микро (открыл цены — `url`, клик по телефону/мессенджеру — `phone`/`messenger`, время > 1 мин — `visit_duration`)
- Помечай: `niche_template: default`

### Общие правила для всех ниш

**Никогда не делаем как макро:**
- «Вход на сайт» / «Просмотр любой страницы»
- «Клик по любой кнопке»
- «Время > 5 секунд»
- «Просмотр главной страницы»

**Микро почти всегда:**
- **Скролл 75%** — содержательный интерес (JS-событие → разработчик; нет его — заменяй на `visit_duration`)
- **Время > 1 минуты** — отсев случайных
- **Открытие важной страницы** (цены / контакты / о компании)

**Составные обязательны:**
- B2B SaaS с триалом
- Сложная воронка с несколькими этапами
- Дорогие продукты с предварительной квалификацией

В большинстве случаев простой связки «макро + 2-3 микро» хватает. Составную — только когда воронка явно многошаговая и каждый шаг важен.

**Типы целей — кто их «включает»:**

| Тип | Что ловит | Разработчик нужен? |
|---|---|---|
| `url` | посещение страницы (`/thanks`, `/order/success`) | нет |
| `phone` / `email` / `messenger` / `social` / `file` / `search` / `chat` / `payment_system` | клики по телефону, почте, мессенджерам, соцсетям, скачивания, поиск по сайту, чаты, платёжки — Метрика ловит сама | нет |
| `number` | просмотр N страниц (`depth`) | нет |
| `visit_duration` | время на сайте (`duration`, сек) | нет |
| `step` | составная, 2–5 шагов (`steps`) | только если шаги — JS-события |
| `action` | JS-событие `ym(<счётчик>, 'reachGoal', '<id>')` — клики по кнопкам, скролл, отправка формы без страницы успеха | **да** |

Сначала ищи вариант без разработчика (`url`, `phone`, `messenger`, `file`). `action` — только когда иначе никак; если таких целей много — сразу в бриф разработчику.

Если JS-целей нужно много — сразу включить в бриф разработчику.

## Составные цели — когда и как

В Метрике — тип `step`. Многошаговая воронка, каждая ступенька — отдельная цель, пройти по порядку. Алгоритм Директа оптимизируется по **самой глубокой ступеньке**.

### Случай 1: B2B SaaS с триалом

Цикл: Клик → Сайт → Тарифы → Демо → Триал → Не отменил 7 дней → Оплата.

Оптимизируя **только по «Запросил демо»** — алгоритм притащит холодных, которые не оплачивают. CAC огромный.

**Решение:** составная «Демо → Триал → Не отменён за 7 дней». Алгоритм учится приводить тех, кто доходит до 7-го дня — это уже почти платящие.

JS-события в коде:
- `ym(counter_id, 'reachGoal', 'form_demo_submit')` — после отправки формы демо
- `ym(counter_id, 'reachGoal', 'trial_start')` — при первом входе в ЛК триала
- `ym(counter_id, 'reachGoal', 'trial_day7_active')` — через 7 дней, если логинился (cron)

### Случай 2: Сложная B2C-воронка с подтверждением

Премиум-туры, дорогие услуги: Заявка → Менеджер созвонился → Выслал коммерческое → Клиент пришёл на встречу.

«Заявка → Созвон → Встреча» решает проблему холодных лидов.

### Случай 3: Многошаговая регистрация / квиз

Email → телефон → подтверждение → анкета. Бросает на середине — не считается.

### Когда составная НЕ нужна

- **Срочный спрос:** клиент в моменте, либо звонит, либо нет.
- **Простой интернет-магазин «корзина → оплата»:** хватит простой «Оплата успешна».
- **Информационный лидмагнит:** «скачал PDF» — самостоятельная конверсия.
- **Мало трафика:** составная усложняет жизнь алгоритму. Если 5-10 макро в неделю — простая макро.

### Главные ошибки

1. **Слишком много шагов.** 5+ — алгоритм не учится, конверсия 0.1%. **Максимум 3-4 шага**.
2. **Шаги в неправильном порядке.** Метрика учитывает порядок! Если `trial_start` пришло **раньше** `form_demo_submit` — Метрика **не зачтёт**. Ставить шаги в реальном порядке воронки. Нелинейная воронка — лучше две отдельные простые цели.
3. **Конфликт с простой целью того же события.** Если есть простая «Заявка на демо» **и** составная «Заявка → Триал → 7 дней», обе срабатывают на одно событие — Метрика считает обе. Не страшно, но двойные цифры. Решение: в составной — только шаги 2-3, первый держать отдельно.
4. **Не настроен последний шаг.** Самая частая. Делают составную с финальным «Оплата прошла», а в коде нет `payment_success`. Цель **никогда не срабатывает**. ДО создания через API убедись, что **все JS-события** реально отправляются (DevTools → Network → mc.yandex.ru/watch или «Карта целей» Метрики).

### Шаблоны составных по нишам

- **B2B SaaS:** Демо-заявка → Триал-старт → 7-й день активности
- **Премиум B2C с менеджером:** Заявка → Созвон состоялся → Встреча назначена
- **Сложный лидмагнит:** Email введён → Подтверждён → Скачал материал
- **Интернет-магазин с регистрацией:** Регистрация → Первый заказ → Оплата прошла
- **Курсы / обучение:** Заявка → Записан на пробный → Пришёл на урок → Купил курс

### Создавать или нет — 4 вопроса

1. **Длинный цикл сделки (>7 дней)?** Нет → простая.
2. **Воронка реально многошаговая (3+ независимых этапа)?** Нет → простая.
3. **На сайте уже стоят JS-события для всех шагов?** Нет → сначала разработчик.
4. **Будет ≥10 конверсий в неделю по этой составной?** Нет → алгоритм не выучит.

Все 4 «да» → составная полезна. Хоть один «нет» → простая макро + 2-3 микро дают тот же результат.

### Как составная цель идёт в Direct

В `bidding-strategy` для Фазы 3 указываем `goal_id` составной. Direct видит её как одну цель и оптимизируется по ней.

В отчётах Директа эта цель в столбце «Конверсии» — но цифра меньше, чем у простой «Заявка», потому что не все доходят до конца воронки.

**Важно:** для B2B SaaS на Фазе 3 **ВСЕГДА** используем составную, не простую «Заявку». Это правило агентства.

## Особые случаи

### Метрики на сайте нет

Стоп. Без счётчика кампания не работает:
```
АЛЯРМА: На сайте {url} не обнаружена Яндекс.Метрика.
До запуска:
1. https://metrika.yandex.ru/list/
2. Создать счётчик
3. Поставить код на сайт
4. Подтвердить — продолжим настройку
```

### Метрика есть, цели мусорные

Например, «вход на сайт» (срабатывает у всех), «клик на любую кнопку» (срабатывает у ботов). Помечаем `not_usable_for_optimization` и **не используем**. Создаём новые с нуля.

### Доступ к счётчику только на просмотр (`permission: view`) или нет write-токена

Режим **рекомендаций**:
- Аудит делает (чтения хватит — включая `goals_get` со статистикой)
- План целей выдаёт
- Создание — не делает. Выдаёт инструкцию: «зайди в Метрику, создай эти цели руками, пришли goal_id, я привяжу к Директу». После — `goals_get`, чтобы сверить, что цели созданы как в плане

### Счётчик принадлежит другому аккаунту

Тег на сайте есть, а в `counters_get` счётчика нет. Владелец добавляет доступ: `Настройки → Доступы → Добавить пользователя → Редактирование` — на тот аккаунт Яндекса, что подключён в интеграциях click.ru (`accounts_get` покажет какой; как подключать — https://help.click.ru/97#connect-yandex-metrica). Без прав — режим рекомендаций.

### MCP Метрики есть, но «не подключена Яндекс Метрика»

`accounts_get` вернул пустой список с подсказкой про интеграции click.ru. Маркетолог подключает аккаунт Яндекса с Метрикой в интеграциях click.ru по инструкции https://help.click.ru/97#connect-yandex-metrica (ссылку даём всегда) — после этого тот же MCP заработает без перенастройки. Пока не подключил — фолбек по цепочке (API-токен → UI) с пометкой о пропуске.

### Несколько счётчиков на одном сайте

Бывает (миграция, разные команды). Подскажет `report_bytime` по визитам за 7 дней у каждого: живой обычно один. Спроси маркетолога, какой — основной. Привязываем к Директу только основной.

### Один счётчик на нескольких сайтах (мульти-домен)

Норма для холдингов. Не проблема — Метрика умеет, цели работают для всех доменов.

### Тип конверсии — оплата на расчётный счёт

Это **офлайн-конверсия**. Скилл сам её не создаст — нужен импорт из CRM или коллтрекинга. Помечаем: «нужна интеграция CRM с Метрикой (webhook или batch-импорт офлайн-конверсий)».

## Стиль работы

- **Не создавай цели тихо.** Каждое создание — после `dry_run` и явного «ок».
- **Не удаляй ничего в Метрике.** Мусорную цель просто не используем; удаление ломает кампании, которые на неё уже оптимизируются.
- **Судим по цифрам, а не по названиям.** «Заявка» с нулём достижений за 30 дней — мёртвая, как бы её ни назвали.
- **Не используй мусорные цели.** Даже если их 10 — алгоритм оптимизируется не туда.
- **Цели = воронка, не «всё подряд».** Меньше — лучше, если каждая чёткая.
- **Алярма про «нет Метрики» — критична.**
