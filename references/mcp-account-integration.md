# MCP в пайплайне — сценарии по шагам

Этот reference — про то, **что делать** через MCP на конкретных шагах. Сигнатуры инструментов, единицы измерения, `dry_run` и границы возможностей — в `yandex-direct-mcp.md`, здесь они не дублируются.

## Когда применять

Перед тем как опираться на эти сценарии, **проверь, есть ли у тебя способность вызывать инструменты MCP-сервера `yandex-direct`** (в одной из сред они видны как `mcp__yandex-direct__*`, в другой имена могут выглядеть иначе — смотри по короткому имени инструмента: `campaigns_get`, `keywords_get` и т.д.).

Сервер — **хостовый** `https://direct-mcp.aihub.click.ru/mcp`, подключение и заголовки — `yandex-direct-mcp.md` → «Подключение» и `docs/hosted-mcp-setup.md` репозитория пакета. Два следствия хоста, важные для сценариев ниже: `forecast_bids` недоступен (прокси Click.ru) и `adimages_add` не видит локальные файлы маркетолога — картинки заливаются по `image_url` через мост KeepImage (см. Use case 5).

**Если таких инструментов нет** — скилл работает без live-данных: Шаг 2 уходит на справочник CPC из `references/frequency-calculator.md`, Шаг 5 берёт регионы по справочнику, Шаг 8 дедуплицирует ключи по выгрузке от маркетолога, Шаг 10 идёт в Директ Коммандер по `references/direct-commander-import.md`. Каждый такой шаг получает пометку о пропуске в свой артефакт, а сводный список — в `10_launch_log.md`, раздел «Пропущено из-за среды». Формат пометки — в разделе «Что нужно от среды» корневого `SKILL.md`.

Безопасные читающие инструменты (ничего не меняют): `campaigns_get`, `keywords_get`, `keywordbids_get`, `forecast_bids`, `dictionaries_regions`, `adextensions_get`, `report_campaign`, `report_ad`, `report_search_queries`, `report_custom`, `bidmodifiers_get`.

## Use case 0: Выбор кабинета (Шаг 0.5) — до любого другого вызова

**Зачем:** на одном подключении может быть несколько рекламных кабинетов, а каждый
инструмент принимает `client_login`. Не выбрали явно — Шаг 10 создаст кампанию в кабинете
по умолчанию, и узнаешь ты об этом после заливки.

```
accounts_get({})
```

Ответ: `{ source: "yandex-direct" | "yandex-direct-agency" | "click.ru", accounts: [{ client_login, name, ... }] }`.

- `source: "click.ru"` — подключение работает через прокси. Следствия: `forecast_bids`
  недоступен, отчёты требуют `campaign_ids`.
- `source: "yandex-direct"` / `"yandex-direct-agency"` — прямой OAuth. `forecast_bids` доступен.

**Один кабинет** — берём его молча, пишем в `_state.json`.
**Несколько** — гейт: «Вижу N кабинетов: <перечисли name + client_login>. В какой заливаем?»

Записать в `_state.json`:

```json
{
  "direct_client_login": "porg-xxxxxxx",
  "direct_account_name": "Planfix",
  "direct_mode": "click.ru",
  "direct_forecast_available": false
}
```

**Дальше `client_login` из `_state.json` передаётся в КАЖДЫЙ вызов инструментов Директа,
относящихся к кабинету** — и читающих, и пишущих. Не полагайся на «кабинет подключения».
Исключение — три инструмента, которые к кабинету не привязаны и параметр `client_login`
не принимают: сам `accounts_get`, `forecast_bids` (чистый расчёт по фразам) и справочники
`dictionaries_*`. Им `client_login` не передавай.

**Несколько серверов Директа в сессии.** Бывает, что подключено 2–3 сервера в разных
режимах. Тогда: позови `accounts_get` на каждом, покажи маркетологу сводку «сервер → режим
→ кабинеты» и спроси, в какой кабинет какого сервера заливаем. Запиши выбранный сервер в
`_state.json` → `direct_server`. Исключение — `forecast_bids`, см. Use case 3.

**Стоимость:** ~10 баллов. Этот вызов заодно проверяет связность MCP — отдельного
пинга не нужно.

## Use case 1: Аудит аккаунта (Шаг 2)

**Зачем:** понять, есть ли в аккаунте кампании, семантически пересекающиеся с новой. Нужно, чтобы на Шагах 3–4 не дублировать ключи (каннибализация — конкуренция с самим собой за показ), а на Шаге 2 взять реальные ставки и CPC как ground truth.

```
campaigns_get({ client_login: <из _state.json>, limit: 100, include_strategy: true })
```

`include_strategy: true` заодно вернёт стратегии, счётчики Метрики и приоритетные цели существующих кампаний — полезно, чтобы не спорить с уже настроенной логикой аккаунта.

Сохрани в `<workspace>/_account_audit.md`:

```markdown
# Аудит аккаунта (на момент запуска пайплайна)

Всего кампаний: N
Активных (State=ON): K
Черновиков (State=OFF): M
Архив: L

## Возможно семантически близкие к новой
- Id 709899154 «KM-Search-P1-SMM-Freelancer» — DRAFT, стратегия WB_MAXIMUM_CLICKS, счётчик 87654321
- ...

## Прочие (для общего контекста)
- Id 709833190 «LD | Поиск | Мск | Панно» — другой бизнес
```

Спроси: «Вижу N кампаний, из них K похожи на новую (`<имена>`). Учитываем их при подборе ключей и прогнозе CPC?» — ответ сохрани.

Пустой ответ — свежий аккаунт, use case пропускается.

## Use case 2: Дедупликация ключей (Шаги 3 и 8)

```
keywords_get({ client_login: <из _state.json>, campaign_ids: [709899154, 709899157], limit: 500 })
```

⚠️ **Не больше 10 кампаний за вызов** — длиннее список, и API отвечает кодом 4001. На кабинете из полутора-двух десятков кампаний читай порциями по 10 и склеивай результат сам. То же для `adgroups_get`, `ads_get`, `keywordbids_get`. И хотя бы один фильтр обязателен всегда: без него уходит пустой `SelectionCriteria` и API отвечает кодом 8000. Подробности и что меняется в MCP 0.5.1 — `yandex-direct-mcp.md` → «Чтение: всегда передавай фильтр».

Что делать с ответом:

1. **Игнорируй `---autotargeting`** — служебная запись автоподбора, не ключ.
2. **`Bid` в микроединицах**: `300000` = 0.30 ₽. Если все ключи на одной ставке 0.30 — ставки не оптимизированы, брать по ним прогноз CPC нельзя.
3. **Сравни с новым списком** из Шагов 3–4 после нормализации (lowercase, убрать кавычки и операторы, trim):
   - **дубли** — не добавлять;
   - **близкие варианты** — можно оба;
   - **что есть у клиента, чего нет у тебя** — кандидаты в семантику.

## Use case 3: Оценка CPC (Шаг 2)

Порядок источников — по убыванию достоверности. Подробности расчёта и справочник ниш — в `frequency-calculator.md`.

### 1. Историческая AvgCpc — если есть похожие кампании с трафиком

```
report_campaign({ client_login: <из _state.json>, campaign_ids: [...], date_range: "LAST_30_DAYS" })
```

Реально списанные деньги — золотой стандарт. Помечай `from: history`. `campaign_ids`
обязателен, см. правило фильтра в `yandex-direct-mcp.md`.

Нужен CPC по конкретным фразам, а не по кампании целиком — `report_custom`:

```
report_custom({
  client_login: <из _state.json>,
  report_type: "CRITERIA_PERFORMANCE_REPORT",
  fields: ["CampaignName", "Criteria", "Impressions", "Clicks", "Cost", "AvgCpc"],
  campaign_ids: [...],
  date_range: "LAST_30_DAYS"
})
```

### 2. Живой аукцион по существующим ключам

```
keywordbids_get({ client_login: <из _state.json>, keyword_ids: [<из keywords_get>], include_auction: true })
```

Реальная списываемая цена (`Price`) по ключам, которые уже заведены в аккаунт. Ответ объёмный (~44 позиции аукциона на ключ) — **не парси вручную**:

```
python -m scripts.forecast_cpc --input _keywordbids_raw.json --region-factor <множитель>
```

Скрипт вернёт base / optimistic / pessimistic CPC (медиана `Price` на TrafficVolume 75 / 62 / 100). Помечай `from: live-auction`.

### 3. Прогноз по своим маскам — когда в аккаунте ничего нет

```
forecast_bids({ phrases: [<до 100 масок из 01_masks.json>], region_ids: [213, 2] })
```

`forecast_bids` к кабинету не привязан (`client_login` не принимает) — это чистый расчёт
по фразам и регионам. Даёт по каждой фразе `cpc_guarantee_min/max`, `cpc_premium_min/max`, `shows_per_month`, `clicks_per_month`, `ctr` — **без создания кампании и без расхода бюджета**. Для базового сценария бери медиану `cpc_guarantee_max` по фразам, для оптимистичного — `cpc_guarantee_min`, для пессимистичного — `cpc_premium_min`. Помечай `from: forecast`.

🚫 На подключении в режиме прокси click.ru недоступен: сервер отвечает «Прогноз бюджета
недоступен в режиме прокси Click.ru: он живёт в Live API v4». Это не ошибка конфигурации.

✅ **Но если в сессии есть второе подключение Директа в прямом OAuth-режиме**
(`accounts_get.source == "yandex-direct"`, см. Use case 0) — считай прогноз на нём.
`forecast_bids` ничего не создаёт, бюджет не тратит и к кабинету заливки не привязан:
это чистый расчёт по фразам и регионам. Заливка при этом остаётся в выбранном кабинете
прокси-подключения. Зафиксируй в `02_frequency.md`: `from: forecast (сервер <имя>, прямой
режим)`.

Нет ни того, ни другого — источник 4.

### 4. Справочник CPC по нишам

Фолбек из `frequency-calculator.md`. Помечай `from: defaults-table`.

**Источник всегда фиксируется в артефакте** — маркетолог должен видеть, насколько цифре доверять.

## Use case 5: Заливка кампании через MCP (Шаг 10)

**Единственное каноническое описание заливки.** SKILL.md и другие references ссылаются сюда.

**Когда:** Шаги 0–9 пройдены, чек-лист Шага 10А закрыт, маркетолог сказал «заливай».

### 5.0. Pre-flight — до первого вызова

```
python -m scripts.preflight --workspace <path>
```

Проверяет `08_creatives.json` против лимитов Директа: длины заголовков/текстов и слов в них, отображаемую ссылку, быстрые ссылки, уточнения, число изображений и **существование файлов на диске**, наличие `href` или `business_id`, объём минус-фраз, число ключей в группе.

**Хоть одна ошибка уровня error — заливка не стартует.** Возвращайся на соответствующий шаг.

Отдельно проверь по `09_bidding_strategy.json`, что для выбранного типа стратегии есть все обязательные параметры (таблица — в `yandex-direct-mcp.md`, соответствие фаз — в `bidding-strategy.md`). Например `PAY_FOR_CONVERSION` без `goal_id` не создастся.

### 5.1. Подготовка минус-фраз

В Директе три нативных уровня минус-фраз: кампания, группа, ключ. «Аккаунт-уровень» из Шага 6 — это Библиотека минус-фраз, **которую MCP не умеет**. Поэтому уровни схлопываются:

- **Минусы кампании** = `account_level` + `campaigns[<campaign_key>].search` + `campaigns[<campaign_key>].rsya` + `cross_minus_from_other_campaigns`, после дедупликации. В ЕПК Поиск и сети живут в одной кампании, поэтому берутся обе группы минусов, а не одна из них.
- **Минусы группы** = узкие минусы из `08_creatives.json`, только для этой группы.

Лимиты: кампания — 20 000 символов без пробелов, группа — 4096, каждая фраза ≤7 слов. Считай длину **до** вызова. При переполнении режь по приоритету (сначала `account_level`, затем кросс-минусы, затем поисковые) и вынесенное запиши в `10_launch_log.md`: «завести набором Библиотеки минус-фраз вручную».

### 5.2. Гейт с предпросмотром

Прогони весь конвейер ниже с `dry_run: true`. Инструменты вернут тела запросов, ничего не создавая, но выполнив все проверки. Покажи маркетологу сводку:

```
Залью в DRAFT:
- Кампания «<name>», тип ЕПК, стратегия WB_MAXIMUM_CLICKS, недельный бюджет 12 000 ₽, потолок клика 45 ₽
- Счётчик Метрики 87654321, цель оптимизации 100001
- 1 группа, регионы [213, 1], 84 ключа
- 1 комбинаторное объявление: 5 заголовков, 3 текста, 2 картинки, 4 быстрые ссылки, 4 уточнения
- Минусы кампании: 247 фраз (18 400 символов из 20 000)
Заливаю?
```

Только после «ОК» — реальные вызовы.

### 5.3. Последовательность на одну кампанию

Порядок задан зависимостями по ID: ассеты создаются **до** объявления, ставки — **после** ключей.

**Шаг 1. Изображения** (по одному вызову на файл, до 5) — через `image_url`:

Сначала локальные файлы → публичные ссылки KeepImage (скрипт пишет манифест):
```
python -m scripts.upload_creatives_to_storage --workspace <path>
→ assets/storage_manifest.json  { local → url }
```
Затем по одной картинке (строго последовательно — параллель даёт ошибку потока):
```
adimages_add({ client_login: <из _state.json>, image_url: "<url из манифеста>", name: "<имя>", crop: "square" })
→ AdImageHash
```

Картинку, которую маркетолог дал сразу публичной ссылкой, KeepImage не нужен — её URL
идёт в `adimages_add` напрямую. Хостовый сервер `adimages_add` не видит локальные файлы,
но принимает `image_url` (сверено 03.09.2026) — `file_path` работает только в локальном
stdio-режиме. После получения хешей ссылки в KeepImage можно снять (`storage_delete`) или
дать истечь (TTL ≤2 ч). Нет KeepImage и запуска кода — фолбек: объявление без `image_hashes`,
картинки списком ручной работы в `10_launch_log.md`. Полное описание — SKILL.md → Шаг 10Б.

**Шаг 2. Быстрые ссылки** (один набор на объявление, 1–8 ссылок):
```
sitelinks_add({ client_login: <из _state.json>, sitelinks: [
  { title: "Тарифы", href: "https://...", description: "От 990 ₽/мес" },
  ...
]})
→ SitelinkSetId
```

**Шаг 3. Уточнения.** Сначала посмотри, что уже принято модерацией — переиспользование экономит время:
```
adextensions_get({ client_login: <из _state.json>, statuses: ["ACCEPTED"] })
adextensions_add({ client_login: <из _state.json>, callouts: ["Без карты", "Триал 7 дней"] })   // только недостающие
→ ad_extension_ids
```

**Шаг 4. Кампания:**
```
campaigns_add({
  client_login: <из _state.json>,
  name: "<из 05_campaign_structure.json>",
  start_date: "<YYYY-MM-DD>",
  campaign_type: "UNIFIED",
  search_strategy: { type: "WB_MAXIMUM_CLICKS", weekly_spend_limit: 12000, bid_ceiling: 45 },
  network_strategy: { type: "SERVING_OFF" },
  counter_ids: [<07_metrika_goals.json → counter_id>],
  priority_goals: [{ goal_id: 100001, value: 3000 }],
  negative_keywords: [<схлопнутые минусы из 5.1>],
  tracking_params: "utm_source=yandex&utm_medium=cpc&utm_campaign={campaign_id}"
})
→ campaign_id
```

Для ЕПК стратегия обязательна. `priority_goals` передавай **только если известна ценность конверсии**; нет её — оставь `counter_ids` без целей (см. `metrika-goals-setup.md`). Кампания создаётся выключенной — это нормально.

**Шаг 5. Группа:**
```
adgroups_add({
  client_login: <из _state.json>,
  campaign_id: <из шага 4>,
  name: "<имя группы>",
  region_ids: [<Use case 4>],
  group_type: "UNIFIED",
  negative_keywords: [<узкие минусы группы>]
})
→ ad_group_id
```

**Шаг 6. Комбинаторное объявление:**
```
ads_add_responsive({
  client_login: <из _state.json>,
  ad_group_id: <из шага 5>,
  titles: [<3–7 заголовков>],
  texts: [<2–3 текста>],
  href: "<посадочная>",
  image_hashes: [<из шага 1>],
  display_url_path: "<до 20 символов>",
  sitelink_set_id: <из шага 2>,
  ad_extension_ids: [<из шага 3>]
})
→ ad_id
```

**Шаг 7. Ключевые фразы** (пачкой):
```
keywords_add({ client_login: <из _state.json>, keywords: [
  { keyword: "\"автоматизация смм\"", ad_group_id: <ID> },
  ...
]})
```

**Шаг 8. Ставки.** Зависит от стратегии:

- **Автостратегия** (`WB_MAXIMUM_CLICKS`, `PAY_FOR_CONVERSION` и прочие) — ставки не задаются, задаётся приоритет:
  ```
  keywordbids_set({ client_login: <из _state.json>, bids: [{ ad_group_id: <ID>, strategy_priority: "NORMAL" }] })
  ```
- **Ручная** (`HIGHEST_POSITION`) — целевая ставка из `02_frequency.json`, уровень группы закрывает все её фразы:
  ```
  keywordbids_set({ client_login: <из _state.json>, bids: [{ ad_group_id: <ID>, search_bid: 25 }] })
  ```

Это закрывает старую проблему «ключи висят на дефолтных 0.30 ₽».

**Шаг 9. Корректировки ставок** — по одному вызову на тип. Коэффициент **множитель, а не дельта**: `90` = минус 10%, `0` = отключить.
```
bidmodifiers_devices({ client_login: <из _state.json>, campaign_id: <ID>, mobile: { bid_modifier: 90 } })
bidmodifiers_demographics({ client_login: <из _state.json>, campaign_id: <ID>, adjustments: [
  { age: "AGE_0_17", bid_modifier: 0 },
  { age: "AGE_18_24", bid_modifier: 80 }
]})
```
Повторный вызов для того же сегмента вернёт ошибку дубликата — менять значение через `bidmodifiers_get` → `bidmodifiers_set`.

**Шаг 10. `campaigns_resume` НЕ вызывать.** Никогда.

### 5.4. Ошибки и обрыв на середине

- **`success: false`** — остановись, запиши в `10_launch_log.md` причину из `error_message` и остаток баллов из `units`.
- **Частичный отказ** — ответ может быть `success: true`, но содержать отклонённые объекты в `data.*Results[].Errors`. Мост помечает такой ответ ошибкой и перечисляет их. Не рапортуй успех, не проверив текст ответа целиком.
- **Журналируй по ходу, а не в конце.** ID каждого созданного объекта пиши в `10_launch_log.md` сразу. При обрыве заливка продолжается с места остановки: повторный `campaigns_add` создаст **дубль кампании**, а не обновит существующую.

### 5.6. Когда уходить в Директ Коммандер

Фолбек, а не основной путь. Уходим, если:

- MCP не подключён в сессии и `setup_yandex_direct_mcp.py` не помог;
- маркетологу нужен визуальный ревью структуры до отправки на сервер.

## Ошибки и фолбеки

- **MCP не отвечает** — Шаг 2 уходит на справочник CPC; Шаги 8 и 10 останавливаются, сообщи маркетологу, что MCP нужно подключить (`yandex-direct-mcp.md`).
- **Отказ API** — читай `error_message` целиком: мост добавляет причину, остаток баллов и подсказку по коду ошибки.
- **Отчёт не готов** — вернётся `status: "processing"` и `retry_in`; повтори вызов позже или увеличь `wait_seconds`.
- **`forecast_bids` в режиме Click.ru** — недоступен по устройству API, не ошибка конфигурации. Переходи на живой аукцион или справочник.

## Бюджет квот

MCP тратит баллы Direct API (~160k в день, факт — в поле `units` каждого ответа). Типичный пайплайн — 500–2000 баллов, то есть 50–100+ прогонов в день. Справочники в цикле не звать, `dictionaries_regions` кэшировать.
