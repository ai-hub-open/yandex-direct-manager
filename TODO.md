# Часть 1. Чего нет в MCP

Все пробелы подтверждены проверкой по живому списку инструментов — это не устаревшие сведения
из старого gap-анализа. Обойти их из скилла нельзя: MCP-мост универсален внутри
(`client.call(service, method, params)` умеет любой сервис API v5), но наружу выведены только
50 конкретных инструментов, и универсального passthrough среди них нет.

## 1.1. 🔴 Автотаргетинг (`RelevanceMatch`)

**Как устроено.** Автотаргетинг — механизм Директа, который подбирает запросы сам, без вашей
семантики. В единой перформанс-кампании на Поиске и в Картах он **обязателен**: нужна хотя бы
одна категория запросов, выключить его можно только для сетей. Ручные ключи Шага 4 работают
**параллельно** автотаргетингу, а не вместо него; минус-фразы фильтруют и то и другое.

**Почему это проблема.** MCP не управляет автотаргетингом ни в `campaigns_add`, ни в
`adgroups_add`. Кампания, залитая через MCP, формально создастся, но категории запросов
останутся в состоянии по умолчанию. Маркетолог видит «залито через API» и считает работу
законченной — а поведение показов задаёт настройка, которой он не касался. Это самый
неочевидный из пробелов: он не даёт ошибки, он тихо меняет то, кому покажется реклама.

**Варианты.**

- **Оставить как есть, усилить сигнал.** Поле `autotargeting_categories` в
  `05_campaign_structure.json` уже существует, а пункт уходит в `10_launch_log.md`.
  Дёшево, но полагается на то, что маркетолог дочитает лог.
- **Сделать блокирующим гейтом.** После заливки скилл не объявляет кампанию готовой, пока
  маркетолог не подтвердит словами, что зашёл в интерфейс и настроил категории. Медленнее,
  но соответствует весу настройки.
- **Добавить в MCP** параметр автотаргетинга в `adgroups_add` — это отдельная работа в
  репозитории MCP, за рамками скилла.

## 1.2. 🔴 Библиотека минус-фраз (`NegativeKeywordSharedSets`)

**Как устроено.** У Директа три нативных уровня минус-фраз: кампания, группа, ключ. Отдельного
«аккаунт-уровня» нет — переиспользуемый набор реализуется через Библиотеку минус-фраз: до 30
наборов на аккаунт, до 3 наборов на кампанию или группу. Шаг 6 скилла строит именно
«аккаунт-уровень» (универсальный мусор: бесплатно, скачать, своими руками, торрент).

**Почему это проблема.** Сервиса Библиотеки в MCP нет, поэтому при заливке аккаунт-уровень
схлопывается в минус-фразы **каждой** кампании. Следствия два. Первое: универсальный список
дублируется во все кампании, и при правке одного слова нужно обойти их все. Второе: дубли
съедают лимит кампании — 20 000 символов без пробелов. На большом проекте с длинной
кросс-минусацией лимит реально достижим, и часть фраз придётся выносить руками.

**Что уже сделано.** `scripts/preflight.py` читает `06_negative_keywords.json`, собирает набор,
который реально уйдёт в `campaigns_add`, и считает его объём до заливки. При переполнении даёт
ошибку с приоритетом обрезки: сначала `account_level`, затем кросс-минусы, в последнюю очередь
поисковые.

**Варианты.**

- **Текущий (обрезка + ручной вынос).** Работает, но при переполнении часть защиты кампании
  фактически не действует, пока маркетолог не заведёт набор.
- **Уменьшить дублирование на входе.** Сократить универсальный список до действительно
  универсального (сейчас в нём есть нишевые слова) и перенести нишевое на уровень кампаний.
  Снижает вероятность переполнения без правок кода.
- **Добавить `NegativeKeywordSharedSets` в MCP.** Единственное полное решение: набор заводится
  один раз и подключается к кампаниям по ссылке.

## 1.3. 🔴 Пакетные стратегии

**Как устроено.** Пакетная стратегия объединяет несколько однотипных кампаний в один пул
обучения: порог «≥10 конверсий в неделю» считается **суммарно по пулу**, а не по каждой
кампании отдельно. До 100 кампаний в пакете.

**Почему это проблема.** Шаг 9 сам рекомендует пакетную стратегию как решение проблемы
«кампания голодает по данным» — типичный случай, когда одну цель ведут несколько ЕПК по разным
углам, и каждая по отдельности порог не набирает. Залить пакет через MCP нельзя. То есть
рекомендация методички в принципе не исполняется автоматически, и без неё мелкие кампании
рискуют навсегда застрять в обучении.

**Варианты.**

- **Фиксировать в логе.** Поле `package_strategy_id` в `09_bidding_strategy.json` помечает
  кампании, которые должны попасть в общий пул; пункт уходит в `10_launch_log.md`.
- **Не рекомендовать пакет, пока не будет поддержки** — честнее по отношению к автоматизации,
  но хуже по существу: методика от этого не станет верной.
- **Проверить, отдаёт ли API v5 пакетные стратегии вообще.** Возможно, это UI-only механизм —
  тогда нужно зафиксировать это в документации, чтобы вопрос не поднимался снова.

## 1.4. 🟡 Временной таргетинг (`TimeTargeting`)

**Как устроено.** Расписание показов и почасовые коэффициенты ставок задаются на уровне
кампании.

**Почему это проблема.** Для B2B-углов и ниш с рабочими часами (услуги с приёмом звонков)
показы ночью — это слив бюджета. MCP не покрывает ни `campaigns_add`, ни корректировки по
времени. Скилл про временной таргетинг сейчас вообще не говорит, то есть маркетолог может о нём
и не вспомнить.

**Варианты.** Добавить пункт в предзапусковой чек-лист (дёшево, закрывает забывчивость);
либо расширить MCP.

## 1.5. 🟡 Элементы объявления: кнопка, цена, промоакция, карусель

**Как устроено.** Шаг 8 (`ad-copywriting.md` → «Дополнительные элементы») проектирует кнопку
действия (№304), цену (№323), промоакцию (№324, до +30% CTR) и карусель из 2–10 изображений
(№306). В API эти элементы существуют, в обёртке MCP полей для них нет.

**Почему это проблема.** Скилл тратит шаг на проектирование того, что не может залить.
Промоакция — заметный рычаг CTR, и потерять её на последней миле обидно. Дополнительно: скилл
просит не выдумывать цены и акции, то есть данные реальные и уже собраны у маркетолога — тем
досаднее вносить их вручную.

**Варианты.** Оставить проектирование и выносить в лог (сейчас так); либо убрать из Шага 8,
пока нет поддержки (сэкономит время, но потеряет рычаг); либо добавить поля в MCP — это самая
дешёвая из доработок MCP, поскольку речь о полях объявления, а не о новых сервисах.

## 1.6. 🟡 Видео: полупробел

**Как устроено.** `ads_add_responsive` принимает параметр `video_extension_ids`. Но сервисов
`AdVideos` и `Creatives`, которыми видео создаётся и загружается, в MCP нет.

**Почему это проблема.** Параметр выглядит рабочим, а ID для него взять негде — типичная
ловушка «половина цепочки есть». Поле `videos` в `08_creatives.json` заполняется на Шаге 8.5,
но остаётся справочным.

**Что уже сделано.** `preflight.py` выдаёт предупреждение, если `videos` непусты, чтобы
несоответствие всплывало до заливки, а не после.

**Варианты.** Загружать видео через интерфейс и, если нужна автоматизация, добавить `AdVideos`
в MCP. Полумера — принимать в `08_creatives.json` уже готовые ID видео, загруженных вручную:
тогда `ads_add_responsive` их подхватит.

## 1.7. 🟢 Остальное: ID принимаются, объект создать нечем

`business_id` (профиль организации) и `turbo_page_id` (Турбо-страница) — параметры существуют
в `ads_add_responsive` и `sitelinks_add`, но сервисов `Businesses` и `TurboPages` в MCP нет.
Работают, только если ID получен другим путём.

Также отсутствуют: `RetargetingLists` (создание условий подбора аудитории), `AudienceTargets`

# Часть 2. Требует решения владельца методологии

## 2.1. 🔴 Фаза 1 и Фаза 2 стратегии: потолок ставки или средняя цена клика?

**Решить до первого боевого запуска — это единственный пункт TODO, который меняет поведение
реальной кампании и расход бюджета.**

**Как устроено.** В API есть два разных механизма ограничения цены:

- `WB_MAXIMUM_CLICKS` («Максимум кликов») с параметрами `weekly_spend_limit` и **`bid_ceiling`** —
  потолок ставки в аукционе. Алгоритм не поставит ставку выше, но средняя цена клика может быть
  любой ниже потолка.
- `AVERAGE_CPC` («Средняя цена клика») с параметром **`average_cpc`** — алгоритм удерживает
  **среднюю** цену клика около заданной, отдельные клики могут быть дороже.

**В чём расхождение.** Проза `bidding-strategy.md` описывает Фазу 1 как «Максимум кликов с
ограничением **средней цены клика**», а Фазу 2 — как «**ужесточить** это ограничение», то есть
поменять число у той же стратегии. Таблица «Маппинг в API» и JSON-пример в том же файле
трактуют это иначе: Фаза 1 → `WB_MAXIMUM_CLICKS` + `bid_ceiling`, Фаза 2 → **смена типа
стратегии** на `AVERAGE_CPC`.

**Почему это проблема.** Три следствия, каждое ощутимое:

1. Терминология прозы («средняя цена клика») буквально соответствует `AVERAGE_CPC`, а Фаза 1 в
   таблице использует `bid_ceiling` — то есть на старте кампания получает не то ограничение,
   которое описано в методичке.
2. Переход Ф1 → Ф2 в текущем маппинге — это замена типа стратегии, а замена **сбрасывает
   обучение алгоритма**. При этом сам файл в разделе «Анти-паттерны» предупреждает не
   переключать стратегию раньше 2–3 недель, потому что преждевременное переключение сбрасывает
   накопленное. Маппинг противоречит анти-паттерну того же файла.
3. Заливка идёт по JSON, а гейт маркетолог читает прозой. Он подтверждает одно, уезжает другое.

**Варианты.**

| Вариант | Ф1 | Ф2 | Плюсы | Минусы |
|---|---|---|---|---|
| **А. Потолок в обеих фазах** | `WB_MAXIMUM_CLICKS` + `bid_ceiling: 250` | то же, `bid_ceiling: 200` | Обучение не сбрасывается, переход — правка одного числа | Проза «средняя цена клика» остаётся неточной, надо переписать на «потолок ставки» |
| **Б. Текущий маппинг** | `WB_MAXIMUM_CLICKS` + `bid_ceiling` | `AVERAGE_CPC` + `average_cpc` | Ф2 буквально соответствует прозе | Смена типа сбрасывает обучение; противоречит анти-паттерну файла |
| **В. Средняя цена в обеих фазах** | `AVERAGE_CPC` + `average_cpc: 250` | то же, `average_cpc: 200` | Точно соответствует прозе, обучение не сбрасывается, переход — правка числа | `AVERAGE_CPC` на холодном старте даёт меньше контроля над охватом, чем «Максимум кликов» |

Рекомендация — **А** или **В**: обе сохраняют обучение при переходе между фазами, что для
трёхфазной методики важнее терминологической точности. Выбор между ними — вопрос того, что
автор методики имел в виду под «ограничением» на старте.

**Что синхронизировать после решения:** прозу про фазы в `bidding-strategy.md`, таблицу
«Маппинг в API», JSON-пример `09_bidding_strategy.json`, пример предпросмотра в
`mcp-account-integration.md` (раздел 5.2).

## 2.2. 🟡 Ценность микро-целей

**Как устроено.** В `campaigns_add` приоритетные цели передаются парами «цель + ценность
конверсии»: `priority_goals: [{goal_id, value}]`. Параметр `value` обязателен — цель без
ценности API не примет. Ценность берётся из брифа (средний чек или маржа со сделки), и скилл
прямо запрещает её выдумывать: нет данных — `priority_goals` не передаётся вовсе, привязывается
только счётчик.

**В чём расхождение.** `metrika-goals-setup.md` говорит, что микро-цели идут в `priority_goals`
«отдельными элементами, с их собственной ценностью». Но бриф спрашивает **одну** ценность —
за целевое действие. Источника ценности для микро-целей (регистрация, просмотр тарифов,
скролл 75%) в пайплайне нет.

**Почему это проблема.** Микро-цели нужны на старте, пока макро-конверсий мало: алгоритму не на
чем учиться. Но если передать их с выдуманной ценностью, алгоритм начнёт оптимизировать под
дешёвые действия — то есть под скроллы вместо заявок. Это хуже, чем не передавать их совсем.

**Варианты.**

- **Только макро-цель в `priority_goals`.** Самое безопасное: алгоритм учится на том, что
  действительно приносит деньги. Микро-цели остаются в отчётах.
- **Спрашивать ценность каждой цели в брифе.** Точнее всего, но удлиняет бриф и требует от
  маркетолога данных, которых у него часто нет.
- **Считать микро-цели долей от макро** (например, регистрация = 10% ценности заявки). Быстро,
  но коэффициент — гипотеза; если её вводить, то явно помечать как гипотезу в артефакте.

- строка 98 — раздел «Шаг 5. РСЯ-кампания(и) аналогично» в алгоритме построения структуры;

  и отдельной кампанией `vokal-RSYa`; при этом JSON-пример ниже в том же файле уже `channel: "epk"`
  и с другими именами кампаний — .md и .json одного артефакта не совпадают;
- строка 184 — гейт «4 кампании (3 Поиск + 1 РСЯ)»;
- строки 199, 207, 212–214, 227 — разделы про бюджеты: «Одна Поиск-кампания + при необходимости
  одна РСЯ», «Поиск по углам… РСЯ по углам (отдельная кампания на каждый угол)»,
  «1-2 Поиск-кампании + 2-3 РСЯ-кампании».

Эхо в других файлах: `bidding-strategy.md` объявляет входом «список кампаний с типами
(Поиск / РСЯ / Ретаргет)» — такого поля в `05_campaign_structure.json` нет, есть `channel`;
`rsya-creatives.md` говорит «РСЯ-кампании заливаются без визуалов» и «для каждой группы
РСЯ-кампании».

**Почему это проблема.** Агент строит структуру по алгоритму (строка 98) и по примеру таблицы
(строка 109), а не по декларации в начале файла. То есть он с высокой вероятностью создаст
отдельную РСЯ-кампанию — и вся дальнейшая цепочка (минусы, стратегия, заливка) поедет по
кампании, которой в модели ЕПК быть не должно.

**Варианты.**

- **Вычистить прозу под ЕПК.** Правильно, но объёмно: затрагивает 8+ мест в трёх файлах.
- **Вычистить только исполняемые места** (алгоритм построения и пример таблицы), а разделы про
  бюджеты пометить как «исторические ориентиры». Дешевле, но оставляет мину.
- **Оставить и явно описать оба режима**: ЕПК по умолчанию и экспертные варианты «только
  Поиск» / «только РСЯ», с правилом, когда какой. Честнее всего, если раздельность иногда
  действительно нужна.

## 3.2. Сколько групп и объявлений в кампании

**Как устроено.** Базовое правило: «1 угол → 1 РК (1 группа, 1 комбинаторное объявление)».

**В чём расхождение.** Три утверждения не сходятся:

- `SKILL.md` и схема креативов — «1 группа, 1 комбинаторное объявление»;
- `campaign-structure.md` строки 42–50 и 94 — «ВЧ идут в **отдельную группу** того же угла»
  (то есть в РК может быть 2 группы), а при бюджете ≥200к ВЧ выносятся в отдельную кампанию;
- `campaign-structure.md` строка 74 — «технически в группе допустимо до 3 неархивных
  комбинаторных объявлений».

Плюс три ориентира по числу ключей в группе: «10-30 ключей» (правило), `keywords_count_estimate: 84`
(пример в том же файле и в примере заливки), `keywords_per_group: 200` (жёсткий лимит API
в `preflight.py`).

**Почему это проблема.** Правило «1 группа» и исключение «ВЧ — отдельная группа» не
противоречат друг другу по существу, но нигде не сформулированы как правило + исключение.
Агент, прочитав только `SKILL.md`, положит ВЧ в общую группу и потеряет возможность выключить
их отдельно — а ради этого исключение и вводилось. Разброс 10-30 / 84 / 200 не даёт понять,
что норма, а что предел.

**Варианты.** Переписать как «по умолчанию одна группа; исключение — ВЧ выделяются в отдельную
группу того же угла, чтобы их можно было выключить, не трогая остальное»; развести «норму»
(10-30 ключей — про однородность) и «лимит» (200 — про API).

## 3.3. Бриф: 12 пунктов против 11, и стоп-гейт фиксировать негде

**Как устроено.** `SKILL.md` требует задать маркетологу одним блоком **12** пунктов, включая
«лицензируемая/запрещённая тематика + документы». Шаг 0 содержит стоп-гейт: если тема из
полностью запрещённых в РФ (азартные игры, оружие, рецептурные препараты) — пайплайн
останавливается; если лицензируемая — нужно зафиксировать, есть ли документы.

**В чём расхождение.** `references/brief.md` во вводной говорит «заполни **11** пунктов», хотя
нумерованных пунктов в нём 12 (12-й — «(опц.) Ограничения и стоп-слова», это про запрещённые
формулировки в текстах, а не про лицензируемую тематику). Вопроса про лицензируемую тематику и
документы в шаблоне **нет вообще**; в примере готового `00_brief.md` такого раздела тоже нет;
в таблице дефолтов поля нет. Ниже по файлу — «со всеми 11 (12) полями».

**Почему это проблема.** Стоп-гейт Шага 0 — это защита от запуска кампании, которую Директ
всё равно отклонит, а в части тем это ещё и юридический риск. Сейчас гейт опирается на данные,
которые бриф не собирает: агент должен «зафиксировать в брифе», а места для фиксации нет.

**Варианты.** Добавить в `brief.md` пункт про тематику и документы, синхронизировать счётчик
пунктов и пример `00_brief.md`; либо, если тематику предполагается определять автоматически по
`ad-legal-topics.md`, убрать из `SKILL.md` требование спрашивать её и описать, как агент
классифицирует тему сам.

## 3.4. Пример К4 в `bidding-strategy.md` нарушает правила своего же файла

**Как устроено.** Сводная таблица и текст гейта показывают четыре кампании; для четвёртой
(комбинаторная ЕПК, бюджет 32к/мес) предлагается «СТАРТ **сразу** с «Максимум конверсий» с
оплатой за конверсии CPA 2 500 ₽ (сеть нельзя на ручных)».

**В чём расхождение.** Три правила того же файла нарушены разом:

- «на старте — **НЕ** «Максимум конверсий»» — базовое правило методики и главное правило Шага 9;
- при оплате за конверсии недельный бюджет должен быть **≥ 10 × цены конверсии**, то есть
  ≥ 25 000 ₽/нед; 32 000 ₽/мес — это около 7 400 ₽/нед, втрое меньше порога;
- обоснование «сеть нельзя на ручных» файл сам объявляет неактуальным для ЕПК: «отдельной
  оговорки не требуется — сеть внутри той же кампании ведёт автостратегия».

**Почему это проблема.** Это не абстрактная неточность: пример показывает готовый ответ, и
агент склонен копировать примеры буквальнее, чем правила. Скопировав его, он предложит стратегию,
которая не выйдет из обучения из-за недобора бюджета.

**Варианты.** Переписать К4 под правила (старт с «Максимум кликов», переход к оплате за
конверсии после накопления и при достаточном бюджете); либо оставить как редкий случай, но
явно пометить, почему здесь можно, и поднять бюджет в примере до порога.

## 3.5. Ссылки на неверные шаги

**Как устроено.** Пайплайн из 10 шагов, references ссылаются друг на друга по номерам.

**В чём расхождение.**

- `negative-keywords-builder.md` — «Возвращаем в **Шаг 6** (`campaign-structure`)», но
  `campaign-structure` — это Шаг 5; Шаг 6 — сам этот файл.
- Там же гейт заканчивается двумя взаимоисключающими вопросами: «Передаю **в структуру
  кампаний**?» (это предыдущий шаг) и семью строками ниже — «Передаю в **Шаг 7**?».
- `SKILL.md` в таблице references помечает `mcp-account-integration.md` как «Шаг 2 + Шаг 10»,
  хотя Use case 4 (регионы) в нём объявлен для Шагов 5 и 10.

**Почему это проблема.** Скилл поддерживает возобновление работы («продолжаем по Директу» →
читаем `_state.json` → продолжаем с нужного шага). Неверный номер шага в инструкции возврата
отправит агента не туда, а два взаимоисключающих финальных вопроса в одном гейте — это выбор
наугад.

**Варианты.** Точечная правка трёх мест. Дополнительно — проверить остальные межшаговые ссылки
одним проходом, раз уж ошибка встретилась.

## 3.6. `campaign_key` не доходит до человекочитаемых артефактов

**Как устроено.** `campaign_key` введён как сквозной идентификатор кампании: задаётся на Шаге 5
и переносится без изменений в артефакты минусов, целей, креативов и стратегии. Проверено: во
всех JSON-схемах он согласован, старых форматов не осталось.

**В чём расхождение.** Парные `.md`-артефакты, которые читает человек, опознают кампании только
человеческими метками: `05_campaign_structure.md` — колонка «Кампания» со значением вида
`vokal-Search-Premium`; `09_bidding_strategy.md` — «К1 «Премиум»», «К4».

**Почему это проблема.** Маркетолог на гейте подтверждает стратегию по `.md`, а заливка идёт по
`.json`. Сопоставить их вручную можно только по смыслу названия — при 5+ кампаниях это источник
ошибок «подтвердили одно, залили другое». Ровно ту проблему, ради которой вводился сквозной
ключ, `.md`-артефакты воспроизводят.

**Варианты.** Добавить колонку `campaign_key` в таблицы `.md`-артефактов (дёшево, решает);
либо использовать `campaign_key` вместо меток «К1»/«К4» в заголовках и сводках.

## 3.7. Имя промежуточного артефакта масок

**Как устроено.** Шаг 1 прогоняет маски через Wordstat:
`python -m scripts.wordstat_api --mode masks --output 01_masks_freq.json`.

**В чём расхождение.** Весь остальной пайплайн — Шаг 2 (прогноз CPC), Шаг 3 (seed-фразы),
чек-лист Шага 10, карта артефактов — читает **`01_masks.json`**. Шага, превращающего
`01_masks_freq.json` в `01_masks.json`, нигде не описано.

**Почему это проблема.** Либо агент решит, что это один и тот же файл, и будет искать
несуществующий, либо создаст `01_masks.json` по-своему, и содержимое разойдётся с тем, что
реально отдал Wordstat. Чек-лист Шага 10 при этом требует наличия `01_masks.json` и без него
блокирует заливку.

**Варианты.** Переименовать вывод скрипта в `01_masks.json` (одна правка в `mask-builder.md`,
если промежуточный файл не нужен); либо явно описать шаг «сырой вывод `01_masks_freq.json` →
курируемый `01_masks.json`» и что при этом отбрасывается.

## 4.1. Заливка в песочнице Директа

Всё выше проверено статически: схемы инструментов сняты с работающего MCP-сервера, вызовы

Что именно проверить:

1. `python -m scripts.setup_yandex_direct_mcp --mcp-path <путь> --mode sandbox --token <SANDBOX_TOKEN>`
2. Прогнать конвейер с `dry_run: true` и убедиться, что в `request.params` уходят

   `data.*Results[].Errors` и пишет их в `10_launch_log.md`, а не рапортует успех. Это самый
   вероятный источник тихой потери данных при заливке.

## 4.2. Прогноз в режиме Click.ru — ✅ ПРОВЕРЕНО 2026-08-06

`forecast_bids` живёт в Live API v4 и через прокси Click.ru недоступен по устройству API.
Ветка фолбека (переход на живой аукцион или справочник ниш) описана — и теперь проверена
на живом прокси-подключении.

**Что показал прогон** (MCP 0.5.0, только чтения и `dry_run`, ни одной мутации; кабинет

рассуждением. Стенд к этому готов.

# Часть 5. Принятые решения

Записано, чтобы вопрос не поднимался заново.

## 5.1. Прямая заливка через API (`deploy_campaign.py`) — не переносим

**Откуда вопрос.** В параллельном форке скилла, из которого в 0.10.0 пришли Шаг 8.5 и
`forecast_cpc.py`, был скрипт `deploy_campaign.py` на 404 строки: кампания → группа → загрузка
ассетов → комбинаторное объявление с `AdImageHashes` и `VideoExtensionIds` → ключи, всё в DRAFT,
sandbox по умолчанию, поддержка прокси Click.ru. При слиянии встал вопрос, брать ли его.

**Решение: не переносить.** Три причины:

1. Скилл сознательно ушёл с прямого API на заливку через MCP в 0.9.0 — второй путь заливки
   означал бы две несинхронизированные реализации одного шага.
2. Скрипт ни разу не запускался, даже в песочнице. В его докстринге открытые вопросы («если API
   отклонит `Network=NETWORK_DEFAULT`…», «если API ждёт другие Id…»), тестов на него нет.
3. Единственная его часть, которой в MCP-заливке действительно нет, — загрузка видео. Она
   закрыта ручным путём: см. 1.6 и `references/video-generation.md` → «Как видео попадает
   в объявление».

**Когда пересмотреть.** Если в MCP появятся обёртки `AdVideos` / `Creatives` — они закроют
последнюю причину смотреть в сторону прямого API, и вопрос снимется окончательно. Если вместо
этого понадобится автоматизация видео раньше — дешевле добавить сервис в MCP, чем возрождать
второй путь заливки.
