## 0.20.2 — 2026-10-29

**Прямой отказ на просьбу, которую скилл выполнить не может** (aihub-639). Описание для
пользователей — [`docs/releases/v0.20.2.md`](docs/releases/v0.20.2.md).

Баг: на «Удали все объявления» в сессии с залитыми черновиками агент не отказал, а вернулся к
брифу, сверил ТЗ на картинки и предложил генерировать креативы РСЯ. Правила на такую просьбу в
скилле не было, раздел «Возобновление» вёл к `current_step`, а отказ шлюза мог попасть под
правило «Сбои шлюза» (повтор → фолбек шага).

- **SKILL.md, новый раздел «Чего скилл не делает: прямой отказ»** после «Главного принципа»:
  таблица «просят → где руками → что предложить вместо» (удалить, запустить или снять с паузы,
  отправить на модерацию, чужой кабинет); исключение — `_CPC_PROBE_`. Ответ: первой фразой «Нет,
  у меня нет прав на …», где руками, замена вопросом — и стоп, без возврата к плану.
- **SKILL.md, там же — «Вызов отклонён или инструмента нет»:** отказ по правам (`forbidden`,
  `not allowed`, `permission`, `403`, инструмента нет) — не сбой: без повтора, смежного
  инструмента, скрипта и фолбека; ответ человеку по той же схеме.
- **SKILL.md, «Стиль работы»:** «Новая просьба важнее плана». **«Возобновление»:** продолжаем
  только по просьбе продолжить; сообщение с другой просьбой сначала получает ответ.
- **`references/yandex-direct-mcp.md`:** «Сбои шлюза» отличает сбой от отказа по правам;
  `campaigns_delete`, `ads_delete`, `ads_resume`, `ads_moderate` помечены как не вызываемые
  скиллом.
- `README.md` — строка про прямой отказ.

## 0.20.0 — 2026-10-29

**Режим одного шага: только семантика, только минусы, только объявления — без полного
брифа** (aihub-663). Описание для пользователей — [`docs/releases/v0.20.0.md`](docs/releases/v0.20.0.md).

Баг: на «собери семантику для сайта» скилл шёл в полный бриф (бюджет, каналы, цель Метрики),
а на «бюджет не нужен, только семантика» продолжал спрашивать каналы и параметры кампании и
ставил блокер по пустым стоп-полям.

- **SKILL.md, новый раздел «Режим одного шага»** перед Workflow: `step:semantics` (Шаги 1, 3, 4),
  `step:negatives` (Шаг 6), `step:ads` (Шаг 8) — как распознать, входы (≤4 вопроса одним блоком),
  что пропускается. После последнего артефакта этапа — сводка (вместе с гейтом шага) и строка
  «Дальше можно: … — скажи», дальше скилл сам не идёт; `current_step: "<шаг>.done"`. Гейта брифа
  Шага 0 и `10_launch_log.md` в режиме шага нет — пометки о пропуске идут в последний артефакт и
  в сводку. `_state.json` → `mode: "full" | "step:semantics" | "step:negatives" | "step:ads"`;
  папки без `mode` (до 0.20.0) считаются `full`.
- **Стоп-поля Шага 0 — только в `mode: full`.** Стоп-гейт тематики (`ad-legal-topics.md`),
  гейты внутри выполняемого шага и запрет записи в кабинет без «ОК» — без изменений, в любом режиме.
- **Правило «уточнение = смена задачи»** (Шаг 0, «Стиль работы»): «не нужно X / только Y» —
  не повторять вопрос и не ставить блокер, а переключить `mode` и подтвердить одной строкой.
  Блокер по стоп-полю — только когда пользователь хочет полную кампанию и не отвечает.
- **Шаги 2–4 и субагент `semantics`:** в `step:semantics` Шаг 2 пропускается, нужная частотность
  передаётся как `n/a` (без флага НЕДОБОР); бюджет и каналы опциональны — нет их: ключи под Поиск
  и РСЯ, ВЧ на Поиск в `04_keys_excluded.csv` со статусом `vch_no_budget` и пометкой в
  `04_wordstat_filter_summary.md`.
- **`references/brief.md`:** «Стоп-поля полной кампании — без дефолтов»; новый раздел «Короткий
  бриф для режима одного шага» — блок вопросов на каждый `step:*`. Нумерация разделов
  `00_brief.md` прежняя.
- **«Возобновление»:** читает `mode`; в `step:*` следующий шаг сам не предлагает, спрашивает, что дальше.
- Frontmatter `description`: «Умеет выполнять отдельный этап…».

Заодно — неясности, найденные проверочными прогонами:

- **Бриф:** счёт пунктов приведён к одному — 11 вопросов (+12-й по желанию) ложатся в 13 разделов
  `00_brief.md`; список пунктов в Шаге 0 совпадает с шаблоном (тип сайта на месте). Названное в
  первом сообщении не переспрашивается; без чтения сайта 5 пунктов о продукте идут в тот же
  блок, в пункт 1.
- **Частотности без Wordstat у агента:** новый путь «Пробивает маркетолог»
  (`wordstat-browser.md`) — список фраз, регион, формат «фраза — число», `source: manual_user`,
  пометка о пропуске. Ссылки на него — в `mask-builder.md` 4.3 и в таблице среды SKILL.md.
- **`mask-builder.md`:** убран устаревший «режим симуляции»; маски ниже 150, оставленные на
  гейте, остаются в `01_masks.json` со `status: below_threshold` (раньше 4.4 и «Артефакты»
  противоречили).
- **`wordstat-filter.md`:** 1–3 таргетированных НЧ для РСЯ остаются в `04_keys_excluded.csv` с
  пометкой в `notes`.
- **Пороги 150 / 350 / 750 — по широкому соответствию**, как MCP `wordstat_shows_batch` по
  умолчанию (`strict: false`). Браузерный путь больше не велит пробивать в кавычках: числа
  фразового соответствия меньше и с порогами не сравнимы (`wordstat-filter.md`,
  `wordstat-browser.md`, `wordstat-mcp.md`).
- **`ad-legal-topics.md`:** дистанционная торговля — любой интернет-магазин, документов не
  спрашиваем, реквизиты проверяем на Шаге 10А. Образования в перечне тематик Директа нет
  (сверено 2026-10-29) — из вопроса брифа о тематике «образование с лицензией» убрано, пример
  брифа поправлен.
- `_state.json`: доступность Wordstat дописывается на Шаге 1 после проверки, а не в Шаге 0.

  `autotargeting_bid` — только для ручных ставок в РК «только Поиск».
- **Значения по умолчанию** (`campaign-structure.md`, Шаг 5 SKILL.md, сводка гейта): обычная РК —
  целевые + узкие, без брендов + свой бренд; меньше 30 фраз в группе — плюс альтернативные;
  брендовая РК — только целевые и только свой бренд; бренды конкурентов — только по прямой

  сохраняет, но не применяет (10161) — и для фраз, и для автотаргетинга. В логе такой приоритет

- **`yandex-direct-mcp.md`:** разделы `autotargeting_set`, `keywords_get` (`only_autotargeting`,
  `AutotargetingSettings`), `keywords_update` (настройки автотаргетинга), `keywords_add`

## 0.18.1 — 2026-10-20

**ЕПК на поиск и РСЯ собирается без ошибки 4000, preflight ловит быстрые ссылки и
отображаемую ссылку, которые отклонит Директ.** Описание для пользователей —
[`docs/releases/v0.18.1.md`](docs/releases/v0.18.1.md).

- **Стратегии ЕПК:** снят запрет на `NETWORK_DEFAULT`. При автостратегии на поиске это
  единственная сетевая сторона, которую принимает Директ. Раньше агент ставил
  `WB_MAXIMUM_CLICKS` на обе стороны, получал 4000 «strategies are not compatible» и
  откатывался на `SERVING_OFF` — РСЯ в кампании выключалась. В `bidding-strategy.md` и
  `yandex-direct-mcp.md` — таблица сочетаний сторон по справке API: только поиск →
  сеть `SERVING_OFF`; поиск + РСЯ → `NETWORK_DEFAULT` без `limit_percent`; только РСЯ →
  поиск `SERVING_OFF`, автостратегия с `weekly_spend_limit` в сети. Список сетевых типов
  переписан по ней.
- **Сетевая сторона — по `channel` из `05_campaign_structure.json`** (Шаг 9 SKILL.md,
  примеры в `bidding-strategy.md`, `mcp-account-integration.md`, `campaign-structure.md`).
  `SERVING_OFF` в сети — только когда РСЯ в структуре нет. Ручные ставки на поиске
  (`HIGHEST_POSITION`) совместимы только с выключенной сетью — для РК с РСЯ их не ставим.
- **Заливка (Use case 5):** проверка пары сторон до заливки и сверка стратегии через
  `campaigns_get` сразу после `campaigns_add` — мост молча выключает незаданную сторону.
- **`preflight.py`:** заголовки быстрых ссылок 1–4 вместе ≤66 символов, 5–8 тоже;
  `display_url_path` — только буквы, цифры, `-`, `/`, `№`, `%`, `#`, без сдвоенных `--` и
  `//`; в лимит текста 81 не входят «узкие» знаки `! , . ; : "` (их до 15) — правило сверено
  со справкой API `ads.add`. В заголовке узкие по-прежнему считаются. Тесты на каждую проверку.
- **`yandex-direct-specs.md`:** убрана таблица ТГО «Заголовок 1 / Заголовок 2», лимиты
  остались только в модели комбинаторного объявления. Суммарная длина уточнений на мобильных
  исправлена на 76 символов по справке.
- **Несколько групп в РК:** одно правило в `campaign-structure.md` — по умолчанию одна
  группа, отдельная только под другой лендинг или ВЧ; Шаги 5 и 8 SKILL.md ссылаются на него.
  Use case 5 описывает заливку нескольких групп.

## 0.17.0 — 2026-10-06

**Безопасный черновик: стоп-поля, блокеры, финальная проверка, итоговый отчёт.** Скилл не
подставляет критичные настройки сам, ничего не пишет в кабинет без явного «ОК» и в конце
честно отчитывается, что сделал сам, на каких данных и что осталось проверить руками.
Описание для пользователей — [`docs/releases/v0.17.0.md`](docs/releases/v0.17.0.md).

- **Стоп-поля брифа без дефолтов:** что рекламируем, посадочная страница, регион, бюджет, цель
  (что считаем конверсией), тематика. Дефолт региона «Москва + СПб» убран. Не ответил —
  блокер, дальше Шага 0 не идём. В бриф добавлены посадочная страница и целевая аудитория.
- **Блокер — новый статус рядом с пометкой о пропуске.** Нет доступа к кабинету, не подключена
  интеграция Метрики, нет счётчика, нет подтверждённой цели, пустое стоп-поле — черновик
  готовить можно, писать в кабинет нельзя. Блокеры живут в `_state.json` → `blockers` и
  видны в каждой сводке. Цель Метрики никогда не подменяется догадкой по названию.
- **Запись в кабинет — только после явного «ОК».** `forecast_cpc.py` в режиме click.ru
  (временный черновик `_CPC_PROBE_`) теперь запускается только после подтверждения, а не
  после предупреждения.
- **Финальная проверка перед заливкой (10А):** кабинет, кампания (нет дубля имени), посадочная
  (совпадает с брифом, открывается), бюджет (сходится с брифом), цель Метрики, минус-слова,
  юридические риски на лендинге — каждая строка ✅ / ⛔ / 👀 и показывается в предпросмотре
  вместе с кабинетом и посадочной.
- **Проверка посадочной страницы** — новый раздел `references/ad-legal-topics.md`: сведения о
